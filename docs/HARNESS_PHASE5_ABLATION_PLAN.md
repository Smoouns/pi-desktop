## 1. 为什么下一步是共用 SDK 测试框架

`evals/adapters/components.ts` 直接调用模块，历史快照也不启动旧 Desktop/SDK 生命周期。`evals/pilot/sdk-session.ts` 虽然经过真实 SDK，却固定加载当前完整小说扩展、关闭压缩且只有两个特定任务。二者都不能直接成为 B0→B3 公平比较器。

下一步采用固定 `@mariozechner/pi-coding-agent@0.63.1` 的同一 SDK 框架，显式选择被测能力。它衡量的是**相同 SDK 下的增量能力差异**，不是复刻每个历史桌面版本的整体表现；原生 UI/Rust bridge 仍独立验收。模型循环继续交给 Pi，不编写替代循环。

现有 `eval:offline` / `eval:matrix` 保持零网络；现有两任务 live-pilot 的上限和 schema 不放宽。正式比较使用独立版本化清单与结果身份，复用经过测试的传输计数、隔离、Journal、usage 和恢复组件。

## 2. 变体与固定项

| 变体 | 在上一层增加的被测能力 | 接入门槛 |
| --- | --- | --- |
| B0-raw | 原始基线 | 仅隔离的已知缺陷 probe；不参加首轮真实调用 |
| B0-safety-fixed | 最小必要安全修复 | 固定 B0 源码，逐项登记 safety diff；不能混入重试、observation、checkpoint 或监督 |
| B1 | typed tool/session reliability、unknown-outcome 对账 | 共用 SDK 生命周期，证明未暗中加载 B2/B3 钩子 |
| B2 | observation store、完整请求预算 | 明确 observation 与预算钩子的注册、来源和计量单位 |
| B3 | version-aware checkpoint、native compaction 集成 | 实际经历 SDK 压缩/恢复；不能用磁盘 JSON 序列化代替 |
| B3+SUP / B3+SUP+MAINT | 分别增加 Supervisor / context maintenance | 单列 manifest/profile；不得把后期维护修复回填 B3 |

B4 暂不实现。`evals/variants.ts` 中尚不可运行的项在适配器通过测试前继续保持 `not_implemented`；只写 plan 或增加布尔开关不算实现。

全部变体固定：SDK 与 lock、公共 fixture 初态、任务业务目标、角色授权、模型参数、并发、允许的文件边界、上限与评分规则。业务提示相同；功能必需的工具 schema/系统说明差异逐项冻结并公开说明，不能偷偷给某变体额外事实、答案或专用提示优化。

所有变体共有隔离目录、秘密隔离、外部路径禁止、HTTP 硬上限与日志脱敏。这些是评测环境安全线，不是 B2 的产品预算能力，也不算 B0 自身成功保护了用户：

- 产品预算放行/拒绝与外层限额拦截分别计数，外层挡住越界不自动计为任务 pass。
- unknown-write 测试只改公开临时副本。按实际派发和文件状态观察重复副作用；不为所有变体预装 B1 对账逻辑以抹平差异。
- B0 缺少某个 Harness 工具，不代表业务任务必然 `unsupported`。允许其使用共同的基础读写工具完成相同目标，按结果评分；模块专用接口测试仍单列合同轨道。
- 只有任务依赖的生命周期确实不能执行时标记 `unsupported`，缺格不能静默删除，也不能纳入成功分子。

## 3. 分增量实现

### S1：首个代码增量，零真实请求

1. 定义 SDK profile / capability manifest 和工厂边界；在隔离 ResourceLoader 中显式加载。逐项审核生产扩展的工具注册、context、tool_call、resume、compaction 钩子，不能加载当前全量扩展后仅把 label 改成 B0。
2. 提取并审查 B0-raw → safety-fixed 的最小 diff。每个补丁写明原因、对应失败 probe，以及是否影响任务答案或后期能力；无法分离就阻塞相应 baseline，不偷换“当前关闭部分功能”。
3. 先接 B0-safety-fixed / B1。共同的业务任务至少包含一个无故障对照与一个丢写回执案例，经过真实 SDK 的工具分派和结束流程，模型返回仍由合成 stream 驱动。
4. 检查禁止能力没有注册/调用：B0 无 ledger 自动恢复，B1 无 observation/checkpoint/Supervisor/maintenance。增加故意串入后期钩子的负测试，不能只相信 feature matrix。
5. 两 profile × 两任务 × 三轮零网络演练；验证固定顺序、记录缺失/重复/漂移拒绝、预算耗尽、停机、unknown、usage 缺失、只读重建和临时目录清理。不把合成输出用于模型效果结论。

S1 当前只实现上述 SDK 读写与部分生命周期边界。三轮矩阵走真正 AgentSession 的开始/结束和工具分派；跨 project/session/role/generation 迟到结果另外直接驱动 SDK 载入的 handler 测试，不冒充完整桌面恢复。完整 B0/B1 仍保留未完成标记；报告可运行边界后也不自动触发真实批次。

### S2：最小成对真实比较（另行批准）

只在 S1 对应范围通过后，用 `sdk-b0-safety-fixed` 与 `sdk-b1-reliability` 各执行同一对公开任务一次，标题必须保留 SDK 切片范围，不能简称完整 B0/B1 性能比较。真实模型自行决定工具选择，不使用 S1 的固定重放脚本；须新建独立 live runner/批准清单。这是比较框架的首批数据，但重复数不足以支持模型总体优势或显著性结论；不能混入旧 current-sdk pilot。

| 拟定 task | 业务目标 | 机械判定与差异点 |
| --- | --- | --- |
| `P5A-READ-001` | 读取合成世界规则，回答固定字段 | 读取真实文件、答案与固定事实一致、无业务写入、正常停止；提供无故障对照 |
| `P5A-TOOL-001` | 在指定候选文件完成一次标记写入，核实最终结果 | 首次真实临时写入后注入丢回执；检查最终字节、派发次数、重复副作用、恢复/未知终态。普通读回也能通过，不把调用特定 B1 API 当成成功条件 |

这两个 task ID 已用于 S1 合成演练。S2 工装现在使用新的 `sdk-read-write-v2` / `provider-selected-tools-v1` 身份，独立冻结 prompt、工具 schema、故障触发位置、答案检查和停止条件；首批真实样本为 `s2-live-RGcvnD`，每格一次，结果见第十三增量记录。Oracle 只留评分侧，真实模型看不到，脚本回复仅用于明确标记为 dry-run 的工装验证。

执行顺序采用事先冻结的成对交错顺序，反转下一任务的 profile 顺序，避免总把某变体放在前面；单轮无法消除服务波动，应在报告中说明。不得按结果择优重跑。可判定的普通任务失败保留并继续预登记下一项；安全违规、unknown dispatch、计量缺失或冻结漂移立即停止批次，未执行项保留原因。若要改变失败停止策略，必须在新清单中声明。

### S3：B2/B3 与后续独立对照

当前已交付首个限定离线切片：冻结 B1/B2/B3 工厂与显式 SDK 事件接线，覆盖大结果分页、完整合成请求预算，以及手动触发真实 SDK 原生压缩后从独立进程重开会话、阻断陈旧来源写入并重读恢复。103 项检查通过；三轮 27 格矩阵为 15 pass、12 预登记缺能力负例 fail，9 次 native compaction、9 次跨进程重开，全部使用本地固定响应，真实模型调用为 0。源码指纹和回归证据见结果记录第十四增量；不据此标记完整 B2/B3 已验收。

逐步加入大工具结果/请求预算、来源变更、压缩后恢复任务。先用合成模型触发真实 SDK native compaction 和会话恢复，再单独申请真实摘要请求预算。摘要请求、自动重试和其他隐式模型请求必须被同一传输门计数，不能藏在“工具执行”里。

第二个限定离线增量使用独立 v2 profile/清单，补自动阈值压缩、溢出压缩后的一次 continuation，以及四类丢回执写入的跨压缩/跨进程恢复。写入意图必须在派发前持久化，工具错误不能改成成功；来源和操作状态独立于摘要。测试范围与公开合成触发口径见 [生命周期说明](HARNESS_PHASE5_SDK_LIFECYCLE.md)，实测见结果第十五增量。旧 v1/S2 清单和结果不改写。

后续限定工装与首批真实任务见结果第十七至十九增量；受控强杀/迟到结果独立离线增量见 [恢复竞态说明](HARNESS_PHASE5_SDK_RECOVERY_RACES.md) 和第二十增量。四种固定屏障各三轮，真实 SIGKILL、独立重开及另一个后台执行器；回调代际隔离另作 adapter 单测。它们不是任意时刻断电、父 broker 恢复或完整 Desktop 效果对照，不改变原 profile 的能力定义。

业务目标尽可能跨 profile 一致；观察引用等接口专用任务另列，不把更丰富接口的存在当成质量收益。完整 unknown-write/迟到结果竞态与真实自动恢复仍未覆盖。B3+SUP 与 B3+SUP+MAINT 分别接入，长程任务与人工质量 rubric 再单独冻结；不在首批顺便扩成小说章节创作实验。新的真实普通请求或摘要仍需先完成独立离线工装、冻结清单并另获批准。

## 5. 结果口径与进入条件

- 每个 profile/task/repetition 单独报告完成、失败、unknown、unsupported、未执行与原因码，不生成掩盖安全失败的综合分。
- 重复副作用按实际变更计数；重复派发被阻止另计。任务恢复与安全阻塞不同，blocked 不是 pass。
- provider 原字段、SDK 标准化字段、本地估算三栏分开；cache/费用缺失保持 null。仅对同一冻结任务且实际完成的请求比较用量，同时展示失败/缺失分母；不把失败导致的少调用宣传成节省。
- 所有请求在派发前预留并持久化；失败或未知不退还调用额度。普通任务失败后的后续计划仍占原总预算，不做额外补跑。
- 原始答案仅生成有界安全诊断，不记录私人 prompt、认证、原始异常或思维内容；新任务诊断必须有 schema 与反泄漏测试。
- 发布结果前复核 task/index/Journal 哈希链与只读恢复，并保留负结果。1 次重复只允许描述该次运行，不推断总体优势；更大重复批次另行确定顺序、预算与授权。

进入 S2 的硬门是：可审计的 safety diff、两个真正独立的 SDK profile、S1 全部离线门通过、冻结新清单，以及用户对当批调用预算的明确批准。任一缺失，停在离线实现，不以文档或旧 pilot 成功代替。

## 7. S4 独立真实工装与首批进展

原首批方案采用 C / C+Supervisor / C+Supervisor+maintenance 三配置，分别执行正常候选修正与验证、前置条件缺失时停止、上下文压力恢复三个共同任务，每格一次，共九项，按任务轮换配置顺序。原预算总共最多 54 次 HTTP、每格最多 6 次，普通/单或双摘要共用，不额外安排重试、命名或评判模型。新版 8/72 合同及其获准实测单列本节末尾，不回写首批预算或结果。

方案 JSON 已做静态预算/顺序核验，但 `executable=false`，不是已冻结的 live manifest。参考输入/输出预留 3,538,944 / 110,592，按用户给定价格全部输入按非缓存计算约 $3.07，仅是满额预留参考；cache 不可核实时费用保持未知，不承诺金额上限。任务、判据、人工压力合同、旧 adapter 差异、实现命令和离线门详见专门方案。

不强迫模型失败三次来制造 Supervisor 效果；不将标准答案放入写入安全门；不把缺少前提、预算阻断或未触发分支当作创作完成或能力已覆盖。独立工装完成离线回归后，第二十六增量已 prepare 精确批次、核验有效配置，再另行取得批准。
