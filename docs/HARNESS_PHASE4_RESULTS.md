## 实现

- `src/harness/run-supervisor.ts`：七态确定性监管器；默认每次运行最多 32 个模型轮次、96 次工具调用、12 次验证。已计数的调用 ID 不重复计数；终态不能被后续成功或 `agent_end` 覆盖。
- 无进展检测：同一验证对象连续三次正文 SHA、规范化错误、已读版本证据均不变，进入 `NO_PROGRESS`。重复读取、报告时间戳不算新进展；连续相同参数/修复错误也会停止。交替错误不误算相邻三次，但仍受总预算限制。
- `src/extensions/supervisor-runtime.ts`：在当前 Pi 分支的 `pi-desktop-run-status/v1` 自定义记录保存有界状态。恢复未结束运行时阻塞，不能自动重放；仅显式用户输入可开始新一轮。损坏记录和持久化失败保持阻塞。
- 受管扩展当前 **v15**（Phase 4 初版为 v11，诊断/状态修复曾使用 v12/v13）：连接 Pi 的启动、工具分发、轮次结束、上下文、取消、会话恢复和结束事件。保留原生 Pi agent loop、retry 与 compaction；没有新增自动三职能编排。普通非小说项目不建立监管状态或限制 coding 工具。
- 验证器报告 **v3**：记录实际读取字节的 SHA-256，包含正文、章节卡、architecture 等实际依赖；扩展回验依赖版本。BOM/换行等字节变化同样使旧报告失效。
- 完成边界：本轮写作产物需要当前完整机械验证及无未决操作、有效检查点。局部场景 PASS、旧正文 PASS、过期依赖、输出截断都不能作为完成候选。正常只读答复可结束，但不代表整章通过。
- `get_run_status()`：返回状态、计数、原因码及中文下一步说明。用户可用 `/novel-run-status` 直接查看当前/上一轮状态，不发模型请求、不启动新任务。Desktop 通过现有扩展 RPC 弹出只读状态窗口，不增加第二套验收按钮。

`COMPLETED_CANDIDATE` 永远不等于人工验收、语义正确或 Canon 晋升。所有人工验收/回退仍由既有小说工作流处理。

## 升级与手动测试

重新启动新版 Desktop 的 Pi 运行时以加载受管扩展 v15。**已有测试小说内复制的验证器不会被自动覆盖**：旧版报告没有依赖 SHA 时，会明确阻塞完成判定，需要更新该副本的 `.novel/tools/verify-novel-chapter.ts` 后重新完整验证。不要把旧报告手工改成 PASS。

可以用公开 fixture 创建一个全新的副本（目标必须不存在或为空）：

```powershell
.\scripts\prepare-novel-agent-test.ps1 -Source .\fixtures\harness-novel -Destination .\artifacts\harness\phase4-agent-test
```

在副本的写作职能会话中逐项测试：

1. 要求 Agent 调用 `get_run_status()`，应显示运行中并带本轮范围。请求结束后用 `/novel-run-status` 查看停止原因；普通新消息会开始新一轮，而不是偷偷续跑旧任务。
2. 第 002 章是可通过的合成候选：执行 `verify_chapter(chapter="002")`，完整 PASS 后正常结束，应出现“候选完成”；人工验收状态不变。
3. 第 003 章是机械失败样本：在同一请求内要求验证三次、不修改正文或读取新证据，应在第三次后显示“无进展”，不再继续第四次调用。
4. 在验证后修改正文/章节卡，旧 PASS 不应完成当前候选。依赖过期时先重读、刷新检查点，再完整验证；仅刷新来源不能让旧 PASS 重新有效。
5. 中途取消、重开会话或切换项目，旧运行不得自动恢复写入；新请求仍需满足来源重验和未决操作核对。

这些是完整实机验收建议。**Phase 4 初版没有执行真实模型或原生窗口验收**；后续仅完成下文记载的有限场景，不能将其视为五项全覆盖。

### 2026-09-21 后续修正：中止诊断与旧会话职能

实机反馈的 `This operation was aborted` 对应运行记录为 `BLOCKED_PREREQUISITE / CONTEXT_BUDGET`，工具、轮次、验证计数均为 0。旧版记录合并了多种预算错误，因此只能确认验证器未运行，不能据此断言是历史过长、Key 错误或验证器失败。

- 受管扩展更新为 **v12**。区分输入预算超限、无效预算、无效载荷、不支持的媒体，以及工具注册表、工具 schema、系统提示、模型信息缺失；上下文预处理的读取/输出限额也有独立原因。
- `pi-desktop-budget-diagnostic/v1` 仅保存当前项目/会话/职能/运行范围、原因枚举和数字白名单，不保存正文、请求、原始异常或凭据。恢复仅查询当前分支及同一运行；新运行不会继承旧诊断。监管器原有 v1 摘要兼容不变。
- 前台状态与 `/novel-run-status` 显示具体原因和可用的预算数字；`get_run_status()` 也返回诊断。Pi 本身仍可能显示通用 aborted，不能把这层 SDK 文案当成具体失败原因。旧的 `CONTEXT_BUDGET` 记录无法补算历史原因，需要重新触发一次。
- 职能写入使用公开的 `pi.appendEntry`，不再调用只读上下文中可能不存在的 `sessionManager.appendCustomEntry`。历史侧边栏和会话浏览器传递结构化职能；复用进程时职能变化会重新启动，未绑定会话显式清空注入环境变量。
- 后端仅接受活动分支中的结构化职能，不再从标题或正文猜测权限。没有职能记录的旧会话保持未绑定，可由用户执行 `/novel-write` 显式绑定并预填任务；模板不会自动发送。已绑定其他职能的专用会话必须切换到对应 Agent。

重新启动新版 Pi Desktop 后，在之前的旧会话先执行 `/novel-write`，再发送第 019 章完整机械验证请求。如再次中止，直接执行 `/novel-run-status` 查看新原因；不要撤回人工验收，也不要自动提升预算。没有重新调用真实模型或改写私人会话、正文、验收记录。最终 provider 审计仍是尽力取消，不改变 Google 通道的既有限制。

## 当前限制

- 自动化“长程”指真实扩展 loader/runner 与真实文件上的确定性组合故障测试，不是 LLM 长篇写作质量或 token 节省实验。独立真实 Pi Agent loop 测试使用离线合成 provider，第三次错误后中止且不发起第四次请求；这些测试没有外网模型请求。有限人工实机反馈与自动化数据分开记录。
- 恢复状态覆盖当前分支与项目/会话/职能；Pi hooks 的异步延续另以运行代际隔离。原生无运行 ID 的生命周期事件仍依赖 Pi 的有序分发契约，不声称能识别任意外部伪造乱序事件。
- 状态上限 256 KiB，保存摘要、路径与 hash，不保存小说正文或密钥。摘要完整性不是防本机恶意篡改的数字签名。
- 每轮限额目前是代码默认值，暂无用户可配 UI；预算耗尽应缩小任务，不自动换新 run 绕过。
- 旧验证器需更新；未知写入无法证明结果时继续阻塞，没有新增人工 reconcile UI。
- 文件版本检查不是文件系统事务；无法阻止外部进程在最后检查后并发改写。
- Phase 2 Google 通道最终载荷的严格零发包硬闸门仍按既定决定暂缓；本阶段不改变该限制。
- 本次只做本地提交，不推送；没有本轮远端 CI、Linux 本机测试、Rust 发布打包或 Phase 5 消融结果。Rust 单元测试与本地前端构建不等同于这些验收。
