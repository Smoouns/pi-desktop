# E6：与验证对象相关的机械进展（2026-09-25）

对应 AUD-10 / REV-15。本批先建立对抗验收，再改运行监管；不修改冻结实验实现，不引入模型裁判或第二套 Agent Loop。

## 验收合同

1. 同一验证对象的重复失败不因无关读取、不同读取范围、无关文件写入或报告时间戳变化而重置。读取与写入仍分别记账，但不是有效进展凭证。
2. 按对象、验证模式（完整 / 具体场景）、宿主已核对 SHA 的验证依赖、规范化诊断分别跟踪。正文原始 SHA 继续用于来源与完成验收，但仅正文哈希变化不证明修复。
3. 相同诊断连续出现三次应停；交替章节、交替错误或依赖 A→B→A 不应冲掉原对象已有计数。错误中的可解析长度 / 场景数量不足采用确定性差额；差额严格改善可继续，时间戳、空白及无改善编辑不能伪装成修复。
4. 新验证依赖版本、新诊断形态允许有限尝试；同形态指标全部不恶化且至少一项严格改善才重置该形态计数。新形态不等于语义进展，仍受原有 12 次验证、96 次工具、32 轮和容量上限约束。
5. 真正通过、实际机械改善或相关依赖变化的正例可继续；不能把机械改善、分场 PASS 或历史 PASS 升格为完整通过 / 用户验收 / Canon。
6. 重复回执幂等，跨项目 / 会话 / run / generation 无效，终态不可覆盖。新快照有界并可校验；旧快照仍能读取，旧运行不自动恢复，最新损坏不回退旧成功。
7. 完整生产扩展（含压缩构建）及固定 SDK 生命周期使用隔离合成项目验证真实验证器、文件读写与停止门禁。分别报告停止原因、工具 / 验证 / provider 调用数及完成结果；不得以硬上限停止冒充无进展识别。

## 范围与非目标

- 本批的“进展”是机械验证的有界修复信号，不是小说质量、语义正确性或任务已完成。未知诊断只能按规范化文本身份处理，不能推断严重程度。
- 通用工具修复错误仍沿用独立的重试启发式；它不是章节验证进展判定。E5 非权威历史记录不授予进展、写入权限或验收资格。
- 不调用真实模型、不控制桌面、不改真实小说、全局 Pi 或模型配置；不提交 / 推送。真实模型收益、Google 偶发测试波动、原生 Desktop 与跨平台 CI 另行验收。

## 实现

- 管理扩展升级为 v24；随 Desktop 更新并重启 Pi 运行时生效，不需要重新安装项目验证器。继续消费现有 v3 验证报告，宿主重新核对全部 `verification_sources` 的当前 SHA 后才产生机械进展信号。
- 每个运行保存 `对象 + 完整/具体场景模式 + 相关依赖摘要 + 诊断形态` 的独立计数。相关依赖只来自本次验证器实际读取且已核对的来源，排除正文与生成报告。交换章节、场景、错误形态或依赖版本不抹去其他计数；返回旧组合会接上旧计数。
- 正文 SHA、来源凭证、Operation Ledger、TaskContract 的当前完整 PASS 与人工验收规则不变。普通 `evidence()` / `artifact()` 仍可记录活动，但不能重置验证停滞计数；E5 历史记录不参与决策。
- 按验证器的确定格式解析总字数、分场字数、场景数量及非法注释数量的差额。相同诊断形态下，相对历史最好值，所有差额不恶化且至少一项变好，才将计数重置为 1；同值、变差和一好一坏均不算已证明改善。错误消除形成新形态，允许有限尝试；返回旧形态仍受原计数约束。其他诊断只规范化空白并哈希完整身份，保留具体场景 / 目标的区别，不臆测严重性。
- 相同组合第三次无机械改善以 `NO_PROGRESS / UNCHANGED_VERIFICATION` 停止。原 12 次验证、96 次工具、32 轮硬上限与 256 KiB 快照上限不变；每份机械诊断最多 128 项。新形态 / 新依赖并不保证质量提升，也无法绕过硬预算。仅满足长度可能是灌水，不代表写作质量；这一点仍由人工验收负责。
- 新快照 payload 为 schema 2，沿用 `pi-desktop-run-status/v1` 日志信封；读取器同时校验旧 schema 1 的原始 seal，不修改旧历史。旧 RUNNING 恢复仍转 INTERRUPTED_RUN，只有明确的新输入能开始新运行；最新损坏 / 不支持版本不回退。`get_run_status` 返回策略标识、对象与跟踪数，并明确 `semanticProgressProven=false`。
